## 发现 1｜已完成标定的烙铁上电自检通过后，加热器仍保持禁用

**级别：P1（功能阻断）**  
**位置：** `main/work_task.c:749–829, 1048–1106, 1152–1180`；`ctrl/heater.c:23–52, 60–71`；`main/ui_task.c:69–82`

**调用路径：**
1. 真机模式启动后 `Heater_Init()` 初始将 `heater.enabled=true`。
2. 上电自检的 `SELFTEST_HEAT_READ` 读取测量脉冲后执行 `Heater_Disable()`，把 `heater.enabled` 置为 `false`。
3. 电压自检通过后，`boot_cal_eval()` 只设置 `boot_cal_pending` 并清 `tip_guide`；当当前型号已有电流参考值时，`boot_cal_pending=false`。
4. UI 只在 `boot_cal_pending=true` 时进入 Cur Cal；已标定设备不进入该页面，也就不会经 `WorkTask_SetCalSuppress(false)` 再次使能加热。
5. 后续 PID 虽调用 `Heater_SetPower()`，但该函数在 `heater.enabled=false` 时只更新功率缓存并保持 PWM CCR=0。

**结果：**当前型号已有电流标定值的设备，正常重启并通过自检后仍不加热。首次未标定路径可能因为退出 Cur Cal 而意外恢复加热，因此首轮联调不一定暴露此问题。

**建议：**在自检“全部通过”路径集中完成加热器状态恢复；只有无锁存故障、型号/校准门通过且不处于 Cur Cal/Tip Cal 引导断热时才恢复。恢复前先把保留的测量脉冲功率清零，避免 `Heater_Enable()` 重放旧功率；随后让正常 PID 输出接管。

## 发现 2｜过温故障被清除后，加热器使能位没有恢复

**级别：P1（故障恢复失效，可能随后误报加热器故障）**  
**位置：** `main/work_task.c:921–929, 1460–1476`；`ctrl/heater.c:30–52, 60–71`

过温分支在 `meas_temp > OVER_TEMP_LIMIT` 时调用 `Heater_Disable()`，将加热器设为禁用。随后 `WorkTask_Recover()` 对“仅过温故障”走快速恢复分支：清 `overtemp_fault`、重置诊断基准后直接 `return`，没有重新使能加热器。此后 PID 即使计算出非零功率，`Heater_SetPower()` 仍因 `enabled=false` 不写入 PWM。没有温升时，诊断计时还可能再次锁存 `heater_fault`。

同类问题也存在于链路类故障恢复：`WorkTask_Retry()` 清运行期故障并重跑自检；自检测量阶段会禁用加热器，而自检通过路径没有明确恢复动作（与发现 1 同根因）。

**建议：**恢复逻辑应在传感器/链路重新确认有效后，把缓存功率先置 0，再明确恢复输出使能；不要只清故障标志。为“过温快速恢复”和“重跑自检成功”分别加用例，验证 PWM 从 0 回到受 PID 控制的输出，而不是重放旧占空比。

## 发现 3｜缺少 T12 电流基准时，高温型号的 T12 防错保护会退化为放行

**级别：P1（安全设计缺口；需阻止高温配置绕过）**  
**位置：** `main/work_task.c:155–179, 216–259, 720–726, 771–803`；`page/cur_cal.c:89–127, 230–249`

**触发条件与路径：**
- 三档判型 `classify_tip_cur()` 以 T12 的电流标定参考作为锚；T12 参考值为 0 时返回“无法判型”。
- 退化粗保护 `TYPE_CUR_COARSE_T12_MAX` 当前为 0；`is_t12_scale()` 在 T12 参考和粗门限都为 0 时总返回 false，于是 `type_cur_match()` 最终放行。
- `boot_cal_eval()` 只检查“当前配置型号”的电流参考是否存在，不要求 T12 锚点存在。因此“当前为 T245/T210 且其参考已标定、T12 参考未标定”时，不会再提示标定；自检用 T12 头时也可能无法识别为危险型号。
- 首次标定引导长按可跳过：即使当前型号无参考值会蜂鸣提醒，`cur_cal.c` 仍会返回 HOME 并清除引导标志。

**结果：**在高温型号配置下，型号匹配保护依赖的参考值可能缺失或被用户跳过；插入 T12 头时仍可能无法触发拒绝加热。现有代码注释也明确指出默认粗门限 0 表示“待真机标定前不拦截”。直启后可能暂时被“发现 1”的加热禁用问题掩盖；但离开手柄页等路径会重新使能输出，因此不能视为有效保护。

**建议：**把安全条件与普通“当前型号已校准”分开处理：高于 400°C 的配置必须具备有效 T12 锚点，或使用经硬件验证的非零粗门限；缺失时拒绝高温输出/限制最高温度，而不只是蜂鸣后允许跳过。覆盖“仅 T245 已标定”“仅 T210 已标定”“T12 头插入 450°C 配置”“跳过首次校准”等场景。

## 发布阻塞项｜当前源码默认处于模拟模式

**级别：P0（禁止将当前配置作为真机发布构建）**  
**位置：** `bsp/config.h:7–10`；`bsp/config.c:137–152`；`main/work_task.c:1068–1072, 1104–1106`

当前 `HW_SIM_MODE=1`：配置/校准保存路径会返回成功但不写 Flash；真实自检状态机不执行，启动直接标记自检完成，温度/电压等部分逻辑走模拟值。真机镜像必须用明确的硬件 Release 配置构建，并在构建产物中确认宏为 0；不能依赖手工记得修改默认宏。

## 需进一步确认（未计为已证实缺陷）

`Project.uvprojx` 的目标设备是 `STM32F103RC`，但下载设置包含 `STM32F10x_512.FLM` 和 `-FL080000`；工程 IROM 与数据页规划则止于 `0x08040000`。请在目标 Keil DFP/烧录器上确认算法与实际 Flash 容量完全匹配。配置中的调试时钟元数据也显示 12 MHz，而 `system_stm32f10x.c` 的系统时钟宏配置为 72 MHz；建议核对 Keil 调试/外设时序展示是否采用了实际频率。

## 建议的修复/验证顺序

1. 先建立可恢复的源码基线；不要在当前大量未提交改动上做清理或覆盖。
2. 修复成功自检、过温恢复后的加热使能状态，并确保恢复前清除测量脉冲缓存功率。
3. 为高温型号建立不可绕过的 T12 基准/粗门限安全条件。
4. 固定硬件 Release 配置，确保 `HW_SIM_MODE=0`；执行干净全量构建。
5. 在限流、可控供电和独立测温条件下做上电、重启、过温恢复、传感器断开、错误烙铁头和 Flash 持久化实测。

*本报告指出的是源码路径可推导的问题和配置风险，不构成硬件安全认证。*
