# 编码器输入与 UI 协同 —— 审查报告

> 时间：2026-10-07  
> 现象：菜单导航偶尔卡住无响应（UI 不刷新），但点击/长按仍可用。  
> 方法：静态追踪 编码器采样 → 事件队列 → 菜单内核 → 渲染调度 全链路；未做真机复现。

## 一、数据链路

```
TIM4 编码器计数
   │  Encoder_GetDiff()                    (bsp/encoder.c:45)
   ▼
encoder_process()  ← TIM2 1ms 中断内每 4ms 调用   (main/input.c:139)
   │  evt_enqueue(UP/DOWN)  —— 生产者(中断)
   ▼
evt_q 环形队列(32)  ← SPSC，head/tail 各由一方写   (main/input.c:48)
   │  evt_dequeue()  —— 消费者(主循环)
   ▼
Input_Process()  每轮最多消费 2 个事件          (main/input.c:250)
   │  menu_notify() → Menu_HandleEvent() + UI_RequestRefresh()
   ▼
UI_Task_Process()  渲染合并窗口 2ms             (main/ui_task.c:48)
   │  UI_Render() → menu_list_display() → OLED_UpdateDiff()
   ▼
OLED 差量推送                                   (bsp/oled.c:284)
```

按键与编码器**共用同一个队列**，区别只在 `evt_enqueue` 的事件类型。

## 二、结论

**没有发现"必然永久卡死"的逻辑缺陷**，但存在若干**健壮性缺口**；其中有两处与"旋转失效、按键仍可用"这一症状高度吻合：

1. **队列满时的"丢旋转、保按键"不对称** —— 这是与症状最吻合的机制；
2. **编码器"转向重锚"会吃掉机械抖动下的累计进度** —— 脏编码器会表现为"转不动"。

"UI 不刷新"是旋转失效的**结果**（无事件→无刷新请求），不是独立故障。模拟模式**不直接影响**编码器与 UI 链路，但会掩盖真机路径（见第五节）。

### 补充线索：症状会**自行恢复**、只是**偶尔出现**

这是本次新增的关键信息，它**排除了一整类假设**并**收窄了范围**：

- **排除**：任何永久性状态机死锁、接线断路、初始化错误——这些不会自己好。
- **指向**：一次**瞬态**的资源/时序异常，异常源消失后链路自动复位。

据此把候选重新排序（并剔除在模拟模式下不成立的项）：

| 候选 | 是否自恢复 | 模拟模式下是否成立 | 说明 |
|------|-----------|------------------|------|
| **F3 编码器毛刺→ISR 洪泛** | ✅ 是 | ✅ **成立** | 干扰/毛刺使 `delta` 巨大，ISR 内循环入队上千次、灌满队列；干扰过后自行复位。**模拟模式下唯一能持续灌满队列的途径** |
| **F2 转向重锚吃进度** | ✅ 是 | ✅ 成立 | 机械抖动期进度被反复抵消，转顺了就好 |
| **F1 队列溢出** | ✅ 是 | ❌ **不成立** | 模拟模式无 Flash 擦写、无 `pulse_cur_raw` 200ms 忙等，没有能长时间阻塞主循环的点 |
| F5/F6 显示差量丢帧 | ✅ 是 | ✅ 成立 | 但**只影响显示**，菜单内部仍会前进（见下方判据） |

**一个重要判据**：你提到长按可用。长按在列表里会返回上层、触发整屏重绘。
- 若长按后**画面能正确刷新** → 显示链路（OLED 差量推送）正常，问题在"旋转事件没有到达菜单" → 锁定 **F3 / F2**；
- 若长按后**画面依旧不对** → 显示链路本身有问题 → 转向 **F5 / F6**。

**综合判断：优先怀疑 F3（编码器毛刺引发的 ISR 洪泛 + 队列灌满），其次 F2（机械抖动）。** 两者都与"偶发、自恢复"完全一致，且都与开发板上的编码器接线质量/干扰有关。

## 三、发现（按可能性排序）

### F1｜队列满时优先丢弃旋转事件，按键事件反而保留 — 与症状完全吻合
`main/input.c:65-92`

```c
if(next == evt_q.head)               /* 队满 */
{
    if(event == CLICK || event == LPRESS)   /* 按键: 覆盖队尾旋转事件 */
    { ... evt_q.buf[last].event = event; return true; }
    return false;                    /* 旋转(UP/DOWN): 直接丢弃 */
}
```

队满时：**UP/DOWN 被丢弃，CLICK/LPRESS 通过覆盖队尾存活**。这正是"旋转无响应、点击长按正常"。

但队满需要**主循环长时间不消费**。`Input_Process` 每轮只取 2 个（`input.c:255`），主循环通常极快，队列能迅速排空——所以它只在主循环被**阻塞**时才持续暴露。真机模式下的阻塞候选：
- 页面保存时 `Config_Save()` 的 Flash 整页擦写（STM32F1 单页擦除约 20~40ms，`bsp/flash.c`）；
- `pulse_cur_raw()` 的 200ms 忙等（`work_task.c`，仅真机、型号切换/电流标定触发）；
- 整屏 `OLED_Update()`（软 I2C，约 5~6ms）。

**注意**：模拟模式下 `WorkTask_MeasurePulseCur` 直接返回、`CheckChain` 直接通过，**没有 200ms 忙等**。所以若症状在模拟模式下反而更明显，则本项不是主因，应转向 F2/硬件。

### F2｜"转向重锚"对机械抖动敏感，可能吃掉累计进度
`main/input.c:139-212`

```c
if (dir != 0 && enc_dir != 0 && dir != enc_dir &&
    !(delta >= 4 || delta <= -4))
{
    enc_det_pos = enc_pos + delta;   /* 锚点前移，进度被抵消 */
    delta = -delta;
}
```

只要**相邻两次轮询方向相反**（≥1 计数）且未满一格，锚点就前移，已累计的齿格进度被抵消。设计意图是让反向更跟手，但副作用是：**机械编码器回弹/抖动时，delta 反复被清零，可能长时间攒不满 4 计数 → 一直不出事件**。

数学上 delta 始终有界、持续单向旋转最终仍会出事件，所以它不是"永久死锁"，但足以造成"转半天不动一格"的观感。脏/老化编码器或长引线干扰会显著放大。

### F3｜`Encoder_GetDiff()` 的大毛刺会引发 ISR 长循环 + 批量丢事件
`main/input.c:198-211`

```c
n = delta / ENC_GROUP_TICKS;
while (n-- > 0) evt_enqueue(MENU_EVENT_UP, 1);   /* n 无上限 */
```

若 TIM4 计数因干扰跳变，`delta` 可达数千 → `n` 达数百上千 → **在中断里循环上千次**（数毫秒），期间主循环停摆、队列被瞬间灌满并丢弃大量事件。建议给 `n` 设上限（如 16），超出部分直接重锚丢弃。

### F4｜`Input_ClearEvents()` 非原子，清空可能不彻底
`main/input.c:270-273`

```c
evt_q.head = evt_q.tail;   /* 读 tail 与写 head 之间，中断可能已入队 */
```

注释声称"最多丢弃已入队事件"，但实际上若中断在"读 tail"与"写 head"之间入队，**新事件会被保留**（head 写的是旧 tail）。跳页前想丢弃积压事件的目的会被部分破坏，可能造成目标页误消费。影响较小（窗口极窄），但与该函数的注释承诺不符。

### F5｜OLED 快照在写入后无条件同步，无法发现丢写
`bsp/oled.c:284-297`、`104-119`

软 I2C 是纯 bit-bang，**不读 ACK、无超时**（`oled_i2c_send_byte`）。`OLED_UpdateDiff` 推送后无条件 `oled_snap_sync`，一旦因干扰丢字节，指纹仍被记为"已同步"，该页在内容下次变化前会一直残留旧画面。这会造成"某块区域不刷新"的观感，但会随下一次内容变化自愈。

### F6｜页指纹存在"间隔 32 列换位"的结构性碰撞
`bsp/oled.c:43-54`

```c
s = (s << 5) | (s >> 27);   /* 左旋 5 */
s += v + 0x9E3779B9u;
```

该哈希在 Z/2³² 上线性：字节 i 与 j 的贡献权重相同当且仅当 `i ≡ j (mod 32)`。128 字节页中第 0/32/64/96 列等价，**互换这些列的字节指纹不变**，该页被判为未变化而不推送。单字节改动、相邻换位不受影响（注释里"换位都无法保持指纹不变"的结论对 mod 32 的情形不成立）。实际 UI 中触发概率低，但属真实缺陷。

## 四、模拟模式的影响（针对你的怀疑）

**模拟模式不改变编码器与 UI 的任何代码路径**（`encoder_process`、`Input_Process`、`UI_Task_Process` 均无 `HW_SIM_MODE` 分支）。它影响的是：

- 无 200ms 忙等（`MeasurePulseCur`/`CheckChain` 直接返回）→ 反而**更不容易**触发 F1；
- `check_sleep_shutdown` 直接返回 → 永不休眠，不影响输入；
- 温度在设定值附近**永久 ±4°C 振荡**（`run_pid_cycle` 的模拟分支）→ `temp_reached` 反复翻转、持续触发温度到达蜂鸣，并让 HOME 每 100ms 都在推屏。

所以：**如果你在模拟模式下更容易复现卡顿，那更可能是 F2（编码器抖动）或硬件接线，而不是模拟模式本身。**

## 五、建议的诊断步骤（你有开发板，能直接定位）

**最有效的一招：加三个计数器，一次区分三类原因。** 在代码里加（仅调试用，验证后可撤）：

```c
/* main/input.c */
volatile uint16_t dbg_enc_gen;    /* encoder_process 里每次 evt_enqueue(UP/DOWN) 成功时 ++ */
volatile uint16_t dbg_enc_drop;   /* evt_enqueue 返回 false(丢弃) 时 ++ */
volatile uint16_t dbg_enc_used;   /* menu_notify 里消费到 UP/DOWN 时 ++ */
```

把它们显示到屏幕（HOME 状态行或专门的调试页），卡住时看哪个在涨：

| 现象 | 结论 |
|------|------|
| `dbg_enc_drop` 在涨、`dbg_enc_gen` 也涨 | **F3**：毛刺导致 ISR 洪泛、队列灌满丢弃 |
| `dbg_enc_gen` 不涨 | **F2 或硬件**：编码器根本没出事件（抖动吃掉进度 / TIM4 没计数） |
| `dbg_enc_gen`、`dbg_enc_used` 都涨，但画面不动 | **F5/F6**：显示差量推送丢帧 |

按顺序做，能一步定位到"事件有没有产生 / 有没有被消费 / 有没有被渲染"：

1. **挂调试器，卡住时看三个量**：
   - `enc_pos` / `enc_det_pos`（`main/input.c`）：旋转时 `enc_pos` 是否在变？若不变 → TIM4 没计数（硬件/接线）；若变但 `delta` 长期 <4 → F2。
   - `evt_q.head` / `evt_q.tail`（`main/input.c`）：两者是否长期不相等（队列堆积）→ F1。
   - `menu_ctrl.current`（`menu/menu.c`）：点击时是否在变？变而画面不动 → 渲染问题（F5/F6）。
2. **临时把编码器事件计数显示到屏幕**（在 `menu_notify` 里对 UP/DOWN 累加，HOME 状态行加一位数字）：卡住时看数字是否还在涨，一眼区分"事件没产生"还是"事件没消费"。
3. **确认 TIM4 是否真的在计数**：卡住时读 `TIM4->CNT`，转动编码器看是否变化；不变则查 A/B 相接线与 `Encoder_Init` 的极性配置（`bsp/encoder.c:35` 用了 TI1 上升/TI2 下降，建议核对是否与你的编码器相序匹配）。
4. **对比真机模式**：把 `HW_SIM_MODE` 置 0 复现一次，判断是否与模拟模式相关。

## 六、修复建议（按性价比）

1. **给队列加背压/水位告警**：`evt_enqueue` 满时可考虑丢弃最旧旋转事件而非直接丢新事件，或在持续丢弃时置标志供调试。
2. **给 `n` 设上限**（F3）：`if (n > 16) n = 16;`，防中断长循环。
3. **`Input_ClearEvents` 改为读-写-再校验**：`do { t = tail; } while (t != tail); head = t;` 或直接 `head = tail; __DMB();` 并复核一次。
4. **编码器模型可考虑简化**：若 F2 确认为主因，可改为"纯 4 计数齿格累加 + 静止吸合"（去掉转向重锚的预支），用小幅反向死区换稳定性；代价是急转反向时多走最多 1 格。
5. **OLED 差量可加一次轻量回读校验**（需 SSD1315 支持读），或在丢写时降级为整屏刷新。
6. **页指纹改用乘性哈希**（如 `s = s * 0x01000193u + v;`），消除 mod 32 结构性碰撞。
