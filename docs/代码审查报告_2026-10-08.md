### ❌ F6｜页指纹存在结构性碰撞 —— 仍存在（已量化）
`bsp/oled.c:47-52`：`s = rotl(s,5); s += v + 0x9E3779B9u;`。循环左旋 32 次即恒等（`5×32 = 160 ≡ 0 (mod 32)`），故下标相差 32 的整数倍的两个字节旋转权重相同，交换二者仅靠进位区分。

主机侧实验（排除"两字节相等"的平凡情形）：

| 交换偏移 gap | 碰撞率 |
|---:|---:|
| 1 / 16 / 31 / 33 | ~0 |
| **32** | **≈5.5e-3** |
| **64** | **≈5.8e-3** |
| 单字节改动（对照） | 0 |

**修正既有报告的说法**：不是"交换这些列指纹不变"（那会 100% 碰撞），而是**交换偏移为 32 的整数倍时碰撞率被抬高到约 1/180**，远高于 2⁻³²。代码注释"单字节改动与换位都无法保持指纹不变"对 mod-32 情形不成立。实际 UI 触发概率低，属真实但低危缺陷。**修复**：改用乘性哈希（如 `s = s * 0x01000193u + v;`）。

## 四、本次新发现

### N1｜P2｜编码器「转向重锚」反射判据用错量，快速反向产生错误残差 ✅ 已修复（14:47）
**位置：** `bsp/encoder.c:84-86`

```c
if (enc_acc != 0 && ((delta > 0) != (enc_acc > 0)) &&
    sum > -ENC_TICKS_PER_STEP && sum < ENC_TICKS_PER_STEP)   /* ← 判据错误 */
    enc_acc = (int16_t)(-sum);
```

设计意图（见 :79-83 注释）是"**仅在反向尚未跨过锚点时**反射残差；跨满一格则按净位移结算"。但代码判的是"**反射后残差幅度 < 4**"——二者不等价。当一次轮询的反向计数超过当前残差（`|delta| > |enc_acc|`，即快速反向）时，`sum` 已越过锚点（与 `enc_acc` 反号），此时仍被反射，得到**符号相反的残差**。

**数值复刻验证**（穷举 `acc∈±1..3` × `delta∈-8..8`，与纯位移真值对比，**24 组不符**）：

| 场景 | 当前输出 | 正确值 |
|------|---------|--------|
| `acc=+3, delta=-4` | `step=0, acc=+1` ❌ | `step=0, acc=-1` |
| `acc=+1, delta=-4` | `step=0, acc=+3` ❌ | `step=0, acc=-3` |
| `acc=+3, delta=-6` | `step=0, acc=+3` ❌ | `step=0, acc=-3` |

**后果**：快速反向时残差符号错误 → 后续反向需多走若干格才出事件（额外死区），且在"快速反向再快速正向"的抖动下可能**多报或少报一步**。慢速反向（每 4ms 1 计数，占绝大多数操作）不受影响。

**建议修复（一行）：** 把判据从"幅度 < 4"改为"**未跨过锚点（`sum` 与 `enc_acc` 同号）**"：

```c
if (enc_acc != 0 && ((delta > 0) != (enc_acc > 0)) &&
    ((sum > 0) == (enc_acc > 0)))
    enc_acc = (int16_t)(-sum);
```

经验证，修正后全部 24 组均与真值一致；慢速反向行为完全不变。

> 备注：该判据错误在重构前的 `main/input.c` 锚定模型中**已存在**（旧代码 `!(delta>=4||delta<=-4)` 同样只判残差幅度），重构只是原样搬运，并非本次引入。

**【修复记录 2026-10-08 14:47】** 已按上述建议把 `bsp/encoder.c` 的反射判据改为**同号判断**（`((sum > 0) == (enc_acc > 0))`）并同步更新注释。全量重编 `UV4 -r` → **0 Error / 0 Warning**（Code 23376→23388，+12 B）。数值复核：原 24 组"跨锚点"错误组合**全部消除**；仅余 6 组差异属设计固有的"同号预支"反射（非缺陷）；慢速反向步序与修复前**完全一致**（手感不变）。

### N2｜P3｜「静止吸合」逻辑在重构中被移除（行为回归）

## 五、`menu_ctx` 跳转清理机制 —— 有缺陷（本轮已修正）

`main/input.c` 以"内核状态 + 当前节点/列表父级"构造上下文指纹；`Input_Process` 每消费一个事件后比对指纹，变化即 `Input_ClearEvents()`。指纹本身构造正确（列表内移动不变、跨页/跨列表必变）。

**缺陷（对应症状："进子菜单 / 返回后第一格不动，要再转一格"）**：

队列是 **FIFO**。当"触发跳转的那个事件"被取出处理时，队列里**剩下的事件必然是它之后入队的** —— 即用户**按完之后**才转出来的旋转事件，而不是"旧上下文残留"（那些早就在它前面被消费掉了）。更关键：编码器每出一步已在 `Encoder_GetSteps` 里把对应计数从 `enc_acc` 扣掉，**事件被丢弃 = 这几格计数永久消失**，不会"还回来"。于是"按完 CLICK 紧接着转一格"这一格被吃掉 → 卡一格。进/退都会触发指纹变化，故两端都出现。

**次因**：`enc_acc`（未满一格的残留相位）跨跳转不清零。残留与新转向反号时（如残留 `-1`，正转一格 `4` 计数 → `sum=+3 < 4`）新页面第一格被"还债"吃掉，与主因叠加。

**修正（本轮，2026-10-08 15:0x）**：

- `main/input.c`：跳转时**不再** `Input_ClearEvents()`，改为 `Encoder_RequestResync()` —— 让编码器丢弃半格残留，**保留队列**（跳转后的事件是有效输入）。
- `bsp/encoder.c`：新增 `Encoder_RequestResync()`。主循环置单字节标志，实际复位在取样上下文（`Encoder_GetSteps`）内执行，避免与中断竞争；**只清 `enc_acc`、不动计数基准 `enc_last`**，故"跳转后立刻转的第一格"照常结算。
- `ui_task.c` 的故障跳转 / 首次引导跳转（**非事件触发**，队列里确属旧页面的积压输入）仍显式 `Input_ClearEvents()`，保持不变。

## 八、附带简化：移除 `MENU_FLAG_PASSIVE_VIEW`（15:10，用户要求）

**评估**：该宏（`menu.h:0x08U`）在菜单表中**仅被 1 个页面**使用（索引 14「版本信息」），且该页是**唯一没有 handler 的页面**。它给内核加了一个"绕过 handler、在任意 CLICK/LPRESS 直接退出"的特殊分支，收益 ≈ 省下 6 行 handler 样板，代价 ≈ 1 个 flag 位 + 1 个内核特殊分支 + 文档/概念负担 —— **收益小、净复杂度反而增加**，故移除，行为改由页面 handler 裁决。

**改动**：
- `menu/menu.h`：删除 `MENU_FLAG_PASSIVE_VIEW` 定义（`flags` 仅保留 `DIRECT_HANDLER`）。
- `menu/menu.c`：删除 `menu_state_handler` 中的 PASSIVE_VIEW 分支，事件一律走 ops 回调。
- `menu/menu_table.c`：[14] 去掉该 flag；[6]「固件升级」注释改写（不再引用该宏）。
- `page/settings.c`：`version_ops` 增加 `version_handler`（CLICK/LPRESS → `MENU_RET_DONE`；UP/DOWN → `MENU_RET_OK`），行为与原先完全一致。
- `page/ota_wait.c`、`docs/ARCHITECTURE.md`：注释/文档同步。

**验证**：全工程已无 `PASSIVE_VIEW` 引用；全量重编 `UV4 -r` → **0 Error / 0 Warning**（Code 23428→23418，RO-data −2B）。

> 附注（15:18）：该兜底分支已**一并清理**，见第九节。

## 九、清理死分支并收紧 HANDLER 契约（15:18，用户要求）

承接第八节：`menu_state_handler` 中"LPRESS 且无 handler → 直接退出"的兜底分支（`menu.c` 里 `case MENU_EVENT_LPRESS` 的 `else menu_exit_handler();`）在移除 PASSIVE_VIEW 后已无页面触发，属死代码。本轮一并处理：

- **删除兜底**：LPRESS 并入 UP/DOWN/CLICK 的公共 case，统一走 `ops->handler`，去掉重复的 handler 调用与 `else` 退出。
- **收紧契约（单点把关）**：`menu_activate()` 现在要求页面**同时**具备 `display` 与 `handler` 才允许进入 HANDLER 态。只有 `display` 而无 `handler` 的页面在 HANDLER 态无法响应任何事件（既不能长按退出，也处理不了 CLICK/UP/DOWN），属无效配置 → 一律不激活、回落列表态。
- **消除重复条件**：`Menu_SetCurrentId()` 原先自带一份 `target->ops->display` 判断，现直接调 `menu_activate()`，可激活判定只保留一处。
- **文档**：`menu.h` 的 `menu_ops_t` 注释写明契约；`Menu_SetCurrentId` 的注释同步为 `display+handler`。

**行为影响**：现有页面 `display+handler` 全部齐备，故运行行为不变；仅"无 handler 的页面"（当前不存在）从"LPRESS 可退出、CLICK 无反应"变为"不激活"。

**验证**：全量重编 `UV4 -r` → **0 Error / 0 Warning**（Code 23418→23386，−32 B）。
