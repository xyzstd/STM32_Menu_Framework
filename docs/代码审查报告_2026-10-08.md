### ✅ F6｜页指纹存在结构性碰撞 —— 已修复（15:2x）
原实现 `bsp/oled.c`：`s = rotl(s,5); s += v + 0x9E3779B9u;`。循环左旋 32 次即恒等（`5×32 = 160 ≡ 0 (mod 32)`），故下标相差 32 的整数倍的两个字节旋转权重相同，交换二者仅靠进位区分。

主机侧实验（排除"两字节相等"的平凡情形）：

| 交换偏移 gap | 原实现碰撞率 |
|---:|---:|
| 1 / 16 / 31 / 33 | ~0 |
| **32** | **≈5.5e-3** |
| **64** | **≈5.8e-3** |
| 单字节改动（对照） | 0 |

**修正既有报告的说法**：不是"交换这些列指纹不变"（那会 100% 碰撞），而是**交换偏移为 32 的整数倍时碰撞率被抬高到约 1/180**，远高于 2⁻³²。

**修复（本轮）**：改用 **FNV-1a**（`s ^= v; s *= 0x01000193u;`，偏移基准 `0x811C9DC5`）。复测：偏移 32/64 的碰撞率**降到与其它偏移同一水平**（即仅剩"两字节本就相等"的平凡情形），mod-32 等价类消除；单字节改动、整页逆序/左移仍 100% 改变指纹。成本与原来相当（异或 + 单周期 32bit 乘法）。

## 四、本次新发现

### N1｜P2｜编码器「转向重锚」反射判据用错量，快速反向产生错误残差 ✅ 已修复（14:47）
**位置：** `bsp/encoder.c:84-86`

```c
if (enc_acc != 0 && ((delta > 0) != (enc_acc > 0)) &&
    sum > -ENC_TICKS_PER_STEP && sum < ENC_TICKS_PER_STEP)   /* ← 判据错误 */
    enc_acc = (int16_t)(-sum);
```

设计意图（见 :79-83 注释）是"**仅在反向尚未跨过锚点时**反射残差；跨满一格则按净位移结算"。但代码判的是"**反射后残差幅度 < 4**"——二者不等价。当一次轮询的反向计数超过当前残差（`|delta| > |enc_acc|`，即快速反向）时，`sum` 已越过锚点（与 `enc_acc` 反号），此时仍被反射，得到**符号相反的残差**。

**数值复刻验证**（穷举 `acc∈±1..3` × `delta∈-8..8`，与纯位移真值对比，**24 组不符**）：

| 场景 | 当前输出 | 正确值 |
|------|---------|--------|
| `acc=+3, delta=-4` | `step=0, acc=+1` ❌ | `step=0, acc=-1` |
| `acc=+1, delta=-4` | `step=0, acc=+3` ❌ | `step=0, acc=-3` |
| `acc=+3, delta=-6` | `step=0, acc=+3` ❌ | `step=0, acc=-3` |

**后果**：快速反向时残差符号错误 → 后续反向需多走若干格才出事件（额外死区），且在"快速反向再快速正向"的抖动下可能**多报或少报一步**。慢速反向（每 4ms 1 计数，占绝大多数操作）不受影响。

**建议修复（一行）：** 把判据从"幅度 < 4"改为"**未跨过锚点（`sum` 与 `enc_acc` 同号）**"：

```c
if (enc_acc != 0 && ((delta > 0) != (enc_acc > 0)) &&
    ((sum > 0) == (enc_acc > 0)))
    enc_acc = (int16_t)(-sum);
```

经验证，修正后全部 24 组均与真值一致；慢速反向行为完全不变。

> 备注：该判据错误在重构前的 `main/input.c` 锚定模型中**已存在**（旧代码 `!(delta>=4||delta<=-4)` 同样只判残差幅度），重构只是原样搬运，并非本次引入。

**【修复记录 2026-10-08 14:47】** 已按上述建议把 `bsp/encoder.c` 的反射判据改为**同号判断**（`((sum > 0) == (enc_acc > 0))`）并同步更新注释。全量重编 `UV4 -r` → **0 Error / 0 Warning**（Code 23376→23388，+12 B）。数值复核：原 24 组"跨锚点"错误组合**全部消除**；仅余 6 组差异属设计固有的"同号预支"反射（非缺陷）；慢速反向步序与修复前**完全一致**（手感不变）。

## 五、`menu_ctx` 跳转清理机制 —— 有缺陷（本轮已修正）

`main/input.c` 以"内核状态 + 当前节点/列表父级"构造上下文指纹；`Input_Process` 每消费一个事件后比对指纹，变化即 `Input_ClearEvents()`。指纹本身构造正确（列表内移动不变、跨页/跨列表必变）。

**缺陷（对应症状："进子菜单 / 返回后第一格不动，要再转一格"）**：

队列是 **FIFO**。当"触发跳转的那个事件"被取出处理时，队列里**剩下的事件必然是它之后入队的** —— 即用户**按完之后**才转出来的旋转事件，而不是"旧上下文残留"（那些早就在它前面被消费掉了）。更关键：编码器每出一步已在 `Encoder_GetSteps` 里把对应计数从 `enc_acc` 扣掉，**事件被丢弃 = 这几格计数永久消失**，不会"还回来"。于是"按完 CLICK 紧接着转一格"这一格被吃掉 → 卡一格。进/退都会触发指纹变化，故两端都出现。

**次因**：`enc_acc`（未满一格的残留相位）跨跳转不清零。残留与新转向反号时（如残留 `-1`，正转一格 `4` 计数 → `sum=+3 < 4`）新页面第一格被"还债"吃掉，与主因叠加。

**修正（本轮，2026-10-08 15:0x）**：

- `main/input.c`：跳转时**不再** `Input_ClearEvents()`，改为 `Encoder_RequestResync()` —— 让编码器丢弃半格残留，**保留队列**（跳转后的事件是有效输入）。
- `bsp/encoder.c`：新增 `Encoder_RequestResync()`。主循环置单字节标志，实际复位在取样上下文（`Encoder_GetSteps`）内执行，避免与中断竞争；**只清 `enc_acc`、不动计数基准 `enc_last`**，故"跳转后立刻转的第一格"照常结算。
- `ui_task.c` 的故障跳转 / 首次引导跳转（**非事件触发**，队列里确属旧页面的积压输入）仍显式 `Input_ClearEvents()`，保持不变。

## 十一、隐性 bug 审查（15:5x）

### ✅ H1｜P0｜CRC 覆盖范围包含 `crc` 字段本身 → 每次上电校验必失败，配置/校准全部丢失 —— 已修复（16:0x）

**位置**：`bsp/config.c:124 / 129 / 134`（`config_calc_crc` / `cal_calc_crc` / `typecal_calc_crc`），以及 `:236`（v10 迁移校验）。

```c
return crc16((const uint8_t *)cfg, sizeof(config_t) - sizeof(cfg->crc));
```

**根因**：`sizeof(T) - sizeof(crc)` 只在"`crc` 是结构体最后 2 字节且**尾部无对齐填充**"时才等于"crc 之前的全部字节"。实际布局**有尾部填充**，于是该长度**越过了 crc 字段、把它自己也纳入 CRC 计算**：

| 类型 | sizeof | `crc` 偏移 | 计算覆盖长度 `sizeof-2` | 实际覆盖到 |
|---|---:|---:|---:|---|
| `config_t` | 72 | 68 | 70 | 0..69 ← **含 crc(68..69)** |
| `cal_t` | 64 | 60 | 62 | 0..61 ← **含 crc(60..61)** |
| `type_cal_t` | 16 | 12 | 14 | 0..13 ← **含 crc(12..13)** |

（布局已双重实测：gcc `sizeof/offsetof` = 72/68、64/60、16/12；**ARMCC 的 `Project.map` 也显示 `g_config`=72、`g_cal`=64、`g_typecal`=16**，两者一致。）

**后果**（保存写入的 CRC 是"含旧 CRC 值"算出来的，校验时又用"含新 CRC 值"去算 → 两者必然不等）：

- 主机侧复刻模拟：保存写入 `0x63D1`，下次校验算出 `0x1ACD` → **不相等**；
- 于是 `Config_Load`/`Cal_Init`/`TypeCal_Init` **每次上电都判 CRC 失败** → 调 `*_Reset()` 回落到出厂默认并**再写一次 Flash**；
- 即：**用户设置（温度/PID/休眠/蜂鸣/亮度）、温度校准、电流标定 每次开机全部丢失**，且每次开机多一轮 Flash 页擦写（磨损）。模拟模式下同样如此（`save_page` 不写，但 `Config_Load` 读到空页/不匹配 CRC 仍会 Reset）。
- 附带：v10 旧数据迁移路径（`:236`）同缺陷，其 CRC 校验也永远不通过（不过旧固件同样有此 bug，v10 数据本就不存在）。

**修复**：用 `offsetof(T, crc)` 取代 `sizeof(T) - sizeof(crc)`（需 `#include <stddef.h>`）：
```c
return crc16((const uint8_t *)cfg, (uint16_t)offsetof(config_t, crc));
```
修好后首次上电仍会 Reset 一次（旧数据的 CRC 本就是坏的），此后即正常持久化。**建议同时给 `CONFIG_VERSION` 加 1**，让"修复前/后"的数据显式区分。

**【已实施 16:0x】** `bsp/config.c` 三个 `*_calc_crc` 改用 `offsetof(T, crc)`（补 `<stddef.h>`）；`CONFIG_VERSION` 11→12（旧 v11 数据走 `else` 分支一次性回落默认）。`config_v10_t` 迁移校验**有意保留原 `sizeof-2` 覆盖**（旧固件同缺陷、其数据本就不可能通过，保留原样以免认下按缺陷写出的数据），并加注释说明。模拟/真机两模式全量重编均 **0 Error / 0 Warning**。

### ✅ H2｜P3｜`AD_GetCurrent()` 新鲜标志存在读-清竞态 —— 已修复（16:0x）
`bsp/adc.c`：原 `bool fresh = adc_cur_fresh; adc_cur_fresh = false;` —— 若注入中断恰在此两行之间置位（新导通采样到达），清除会把它抹掉 → 该次读返回 0（"无电流"）。**修复**：把"读+清"放进 `__get_PRIMASK/__disable_irq ... __set_PRIMASK` 临界区（主循环上下文，仅数条指令）。

## 十二、算法优化审查（16:0x）

**总体**：算法主体是扎实的（分段整数 PID + 抗饱和 + 微分先行/不完全微分 + 开环前馈 + Boost + 继电自整定 + 单调样条温度换算 + 去极值平均），**没有明显错误算法**。以下是"能更好"的点，按收益排序。

### ✅ A1｜前馈查表是硬阶跃，交接处有"输出断崖" —— 已改为分段线性插值（16:1x）
`main/work_task.c:1054-1066`：`if (diff>100) ff=900; else if (diff>50) ff=600; else if (diff>25) ff=350; else if (diff>10) ff=180;`，且与 PID 取 `max`。
问题：`diff` 跨过 10°C 时前馈从 **180 直接归零**，输出瞬间最多掉 18%（18% 占空比）；此时 PID 输出通常远小于 180 → 温度会下陷，再靠 PID 爬回来，易在接近设定点处形成小振荡/极限环。
**建议**：把查表改成**线性插值**（尤其给 `0<diff≤10` 加一条 `ff = 18*diff` 的斜坡），让前馈平滑交接到 PID。改动小、无需改结构。

### ✅ A2｜定点截断使积分在小区间"停走"，留下 1~2°C 静差 —— 已加余数累加（16:1x）
`ctrl/pid_controller.c:177`：`pid.integral += (int32_t)cur_ki * error / PID_SCALE;`
`ki` 存的是 ×100（如保守组 0.60→60），当 `|error| < 100/ki`（ki=60 时 `|error|<2`）时该增量被整除截断为 **0** → 积分不再累积，稳态无法消掉最后 1~2°C 偏差（`p_term`/`d_term` 同理有截断）。
**建议**：积分项改用更细分辨率（如内部 ×1000）或加"余数累加器"（把每次整除的余数带入下次），保留亚整数增量；输出时再折算回 ×100。

### A3｜自整定用"翻转帧温度"近似峰值，会高估 Ku
`ctrl/pid_controller.c:404-421`：方向翻转时把**当前帧** `cur_x10` 记为该半周期的极值。真实极值出现在两帧之间，故 `a` 被低估；而 `Ku = 4h×1000/(π·a)` ∝ 1/a → **Ku 偏大 → 整定出的增益偏激进**。
**建议**：在每个半周期内跟踪 running `max`/`min`（每帧更新，翻转时取用），得到真实极值，`a` 更准。

### A4｜温度换算的样条切线每帧重算（效率，非正确性）
`main/work_task.c` 的 `adc_to_temp()` → `spline_interp()`：段斜率 `m[]` 与单调切线 `t[]` **只依赖 6 个标定点**，但每次调用都重算；而每 PID 周期要算两次（温度 + 偏移插值）。
**建议**：标定点/型号变化时缓存一次切线，之后查表插值；顺带把 `cal_offset_interp` 的 6 点样条也一并缓存。

### A5｜Boost 抬升量固定 50°C，可自适应
`BOOST_RISE_DEG 50` 与跌落深度无关。跌得多/少都抬 50°C，偏保守时回温慢、偏激时易过冲。
**建议**：按 `drop = setpoint - meas_temp` 分档或线性映射抬升量（如 `rise = clamp(k*drop, 20, 60)`），更贴合实际负载。

### A6｜`temp_reached` 用单帧瞬时值判到达
`main/work_task.c:1079`：`|meas − setpoint| ≤ 阈值` 即置"到达"并蜂鸣。滤波残余抖动会在阈值附近反复翻转（虽然 `temp_reached_prev` 已去重，但噪声大时仍可能误报）。
**建议**：要求**连续 N 个周期**满足再置位（与 `thermo_open_cnt` 同一手法），更稳。

### 说明（不是缺陷，但值得知道）
- `pid_controller.c` 注释里的"积分分离"实际实现是"大误差时收紧限幅 + 全速段清零积分"（条件限幅），并非教科书式的"按误差开关积分"；口径上可对齐措辞。
- 冷端补偿用 CPU 温度相对漂移近似，系数标注"待真机标定"——这是已知的待标定项，不算算法缺陷。
- ADC 去极值平均（丢 1 大 1 小、余 6 帧均值）+ 一阶低通 0.75 属合理组合，无需改。

## 十四、`Menu_SetCurrentId()` 边界审查（10-09）

针对 `menu/menu.c:64-86` 的强制跳转接口，逐个核对了 5 个调用点（`ui_task.c:64` 故障跳 HOME、`handle.c:124` 换型回 HOME、`cur_cal.c:109/125` 引导保存/跳过回 HOME、`cur_cal.c:248` `CurCal_BootEnter` 进 CUR_CAL）与内核内部路径。

### 已正确覆盖的情形
- **越界拦截**：`id >= menu_max_num` 直接返回，不写非法 `current`。
- **状态配对**：`HANDLER → menu_exit_handler()(调 exit) → NORMAL → menu_activate()(调 enter) → HANDLER`，exit/enter 成对，不会漏调或重复调（幂等早退分支保证"已在目标页且活动"时不空转）。
- **与内核护栏配合**：`menu_state_handler` 末尾的 `if(current != acted_id || state != HANDLER) return;` 与"handler 内自行跳页"衔接，避免对旧节点做无 enter 配对的 exit / 按旧 `child_num` 误下钻。核对 `handle_handler`/`cur_cal_handler` 两处跳页均返回 `MENU_RET_OK`，护栏生效。
- **目标不可激活**（容器 / 无 ops / 缺 display 或 handler）：`menu_activate` 回落 `NORMAL`，`current` 停在目标节点（在父列表中被高亮），不误进 HANDLER。
- **"停在同 id 但非活动态"重激活**：`id==current && state==HANDLER` 才早退；若 `current==id` 而 `state==NORMAL`（如 `CurCal_BootEnter` 时 current 恰为 CUR_CAL），会走完整流程重新 `enter` —— 这正是修掉历史"标志留在半途"缺陷的关键，正确。
- 刷新请求由调用方补（`menu_notify` 派发后 / `ui_task` 显式调 `UI_RequestRefresh`），5 个调用点均覆盖。

### 未覆盖 / 潜在脆弱点
**C1｜P3（防御缺口）｜`id == 0`（占位虚拟根）未被拦截**
范围检查只挡了 `>= menu_max_num`，而 `MENU_NO_PARENT`/`MENU_NO_CHILD` 都等于 0，虚拟根 `[0]` 的 `ops=NULL`。若调用 `Menu_SetCurrentId(0)`：`current=0`、`state=NORMAL`，随后 `UI_Render → menu_list_display` 对 `id=0` 调 `Menu_GetSiblingRange(0)` 返回 **false**（0 不在 `[1,2)` 内）→ **直接 `return 0` 不渲染**，画面冻结在上一帧。当前无调用方传 0，属防御缺口。**建议**：`if (id == 0 || id >= menu_max_num) return;`（或把 0 重定向到 `MENU_HOME_ID`）。

**C2｜P3（潜在重入）｜`menu_exit_handler()` 在 `exit` 回调执行期间 `state` 仍为 `HANDLER`**
`menu_exit_handler`（`menu.c:134-142`）先调 `item->ops->exit()`，**之后**才 `state=NORMAL`。若某 `exit` 回调内再调 `Menu_SetCurrentId`，会因 `state==HANDLER` 再次进入 `menu_exit_handler` → **重复调 exit / 潜在递归**；对称地，`menu_activate` 调 `enter` 时 `state==HANDLER`，`enter` 内调 `Menu_SetCurrentId` 会先对该页做一次"enter 未完成就 exit"。**当前所有 exit/enter 回调都不调用 `Menu_SetCurrentId`（已逐个核查），故仅为潜在脆弱点**。**建议**：`menu_exit_handler` 在调 `exit` 前先置 `state=NORMAL`（或加一个 re-entrancy 守卫标志）。

**C3｜P3（一致性）｜`CurCal_BootEnter()` 无条件 `Input_ClearEvents()`**
该函数在 `handle_handler`（**事件分发中**）被调用时，会丢弃"确认 CLICK 之后"入队的旋转事件 —— 与前面确立的"事件触发跳转不应清队列、只重同步编码器相位"（见第五节 / N5b）原则相悖。属窄路径（仅"切到未标定型号"触发），影响面小。**建议**：把清队列收敛到"非事件触发"的调用点（`ui_task`），`handle.c` 侧只做重同步；或给 `CurCal_BootEnter` 加"是否处于事件分发中"的区分。

**C4｜P4（判据/契约不统一）**
- `menu_back` 用 `flags & MENU_FLAG_DIRECT_HANDLER` 决定是否激活；`menu_activate` 用 `display+handler`。两处判据不同（当前对 HOME 等价，概念上不统一）。
- `Menu_SetCurrentId` 返回 `void`、不自请求刷新：调用方须记得补 `UI_RequestRefresh()`，属隐性契约（易漏）。

**C5｜观察（非缺陷）**
幂等早退 `id==current && state==HANDLER` 意味着**无法用本接口"重进同一页以重置其内部状态"**。当前无此需求（需要时由页面 handler 自行处理），但若将来出现，需另加语义。

### 小结
**主要情形都已考虑到**（越界、幂等、状态配对、护栏配合、不可激活回落、重激活）。**未覆盖的只有边界防御**：`id==0` 虚拟根（C1，唯一会真正导致异常表现的一处）、`exit`/`enter` 回调内的重入（C2，潜在）、`CurCal_BootEnter` 的清队列一致性（C3）。三者当前均无调用方触发，属"加固"性质；**C1 建议顺手补一行**。
