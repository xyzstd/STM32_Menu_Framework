# 设计：上电加热模式（自动 / 手动）

> 状态：**思路记录，尚未实施**（2026-10-23）
> 目标读者：下一次动手实现的人（含未来的自己）
> 关联：`main/work_task.c/.h`、`page/home.c`、`page/settings.c`、`bsp/config.c/.h`

## 1. 需求

- 增加一个页选项：**上电自动加热 / 手动**
- 默认保持现状（自动加热），不影响老用户
- 选"手动"时，上电后**不加热**，必须**点击一次**才开始
- 动机：有人觉得"插电就热"不安全（比如放在桌上、小孩碰到）

## 2. 现状：为什么现在上电就加热

两处叠加：

```c
typedef enum {
    WORK_STATE_ACTIVE,      /* = 0 */
    WORK_STATE_SLEEP,
    WORK_STATE_SHUTDOWN,
} work_state_t;
```

1. `work` 是 static 全局 → **零初始化 → `state == WORK_STATE_ACTIVE`**
2. `WorkTask_Init()` 里**没有**给 `state` 赋值
3. 于是 `WorkTask_Process()` 直接走到 `run_pid_cycle()`，PID 一起步就按设定温度加热

## 3. 方案

### 3.1 新增状态（枚举必须加在**末尾**）

```c
typedef enum {
    WORK_STATE_ACTIVE,      /* = 0 */
    WORK_STATE_SLEEP,
    WORK_STATE_SHUTDOWN,
    WORK_STATE_STANDBY,     /* 新增: 上电待机, 不加热, 等点击 */
} work_state_t;
```

**放在末尾是硬约束**：`ACTIVE` 必须保持 0，否则零初始化的 `work` 会变成待机，默认行为被改掉。

然后在 `WorkTask_Init()` 末尾按配置显式设置：

```c
if (!g_config.power_on_heat)
    work.state = WORK_STATE_STANDBY;
```

### 3.2 停止加热的门

照抄现有 SHUTDOWN 分支的形状（在 `WorkTask_Process` 里 `run_pid_cycle()` 之前）：

```c
if (work.state == WORK_STATE_STANDBY)
{
    Heater_Disable();
    work.power = 0;
    PID_Controller_Reset();
    return;
}
```

放在 `run_pid_cycle()` 之前即可——自检、故障锁存、标定有效性这些门都在它前面，不受影响。

### 3.3 两个必须改掉的冲突（这是本需求最麻烦的地方）

**冲突一：`WorkTask_MarkActivity()` 会把任何输入当成唤醒**

它是唯一的唤醒入口，现在是：

```c
if (work.state != WORK_STATE_ACTIVE) { work.state = WORK_STATE_ACTIVE; ... }
```

如果不改，用户**转一下旋钮就开始加热**，与"必须点击"矛盾。改成只唤醒真正的休眠态：

```c
if (work.state == WORK_STATE_SLEEP || work.state == WORK_STATE_SHUTDOWN)
{ ... 原逻辑 ... }
```

再加一个显式启动入口：

```c
void WorkTask_StartHeating(void);   /* 仅从 STANDBY 迁移到 ACTIVE, 复刻唤醒时的
                                     * SetSetpoint(runtime_temp) + PID_Reset + 故障判断 + Heater_Enable */
```

**冲突二：HOME 的 CLICK 已经被"进菜单"占用**

```c
case MENU_EVENT_CLICK:
    return MENU_RET_DONE;   /* 常驻页结束; 因 child_num>0 由框架自动下钻子列表 */
```

HOME 是 `DIRECT_HANDLER` 且 `child_num>0`，CLICK 等于"下钻到顶层列表"。如果直接把 CLICK 用来启动加热，用户每次进菜单都会顺带开始加热。

**正确做法**：STANDBY 态下让 CLICK 优先用于启动，第二次 CLICK 才进菜单：

```c
case MENU_EVENT_CLICK:
    if (WorkTask_IsStandby()) { WorkTask_StartHeating(); return MENU_RET_STAY; }
    return MENU_RET_DONE;
```

这样交互是：**上电 → 屏幕显示 IDLE → 点一下开始加热（留在 HOME，状态变 Heat）→ 再点一下进菜单**。符合直觉，也不需要额外的"开始"页面。

## 4. 配置项

`config_t` 加一个字段：

```c
uint8_t power_on_heat;   /* 1=上电自动加热(默认) / 0=手动, 需点击启动 */
```

- `default_config.power_on_heat = 1`（保持现状）
- **`CONFIG_VERSION 15 → 16`** → ⚠️ **旧配置清零**（温度、手柄型号、休眠、蜂鸣、亮度全回默认；CAL / TYPECAL 两页保留）。这是既有策略，用户已接受过两次
- `config_clamp()` 不需要处理它（0/1 之外的值按"非 1 即手动"解释即可，或加一行收敛到 0/1）

## 5. 菜单项放哪

**建议放进「系统设置 → 功能设置」**（`func_set_ops`），作为第三行开关。理由：不新增菜单项 → **菜单表、ID、checker 全都不用动**。

该页已有完整的开关机制：

```c
#define FUNC_FIELD_NUM 2                  /* → 3 */
static const char *const fn_label[]  = {"Buzzer:", "Bright:"};   /* → 加 "Heat:" */
static const uint8_t      fn_toggle[] = {1, 0};                  /* → 加 1 */
/* fn_min / fn_max / fn_step 同步加一项 */
```

五个数组都有编译期 guard（`fn_label_guard` 等），漏改一个直接编译失败 —— 这是好设计，不用额外防呆。

**三行布局要改**：现在是 `y = 16 + i*16`（两行居中，上下各 16px）。三行应改成 `y = 8 + i*16`（8/24/40，与「休眠设置」三行同一构图规则）。

## 6. 文案受字库限制（必须先查再定）

HOME 状态行是 `state_text[] = {"NoHnd", "OFF", "Sleep", "OK", "Heat"}`。新增待机态需要第 6 个文案，但 **55 字 ASCII 紧凑表缺不少字母**：

| 候选 | 是否可用 | 说明 |
|---|---|---|
| `Standby` | ❌ | 缺 `b`、`y` |
| `Ready` | ❌ | 缺 `y` |
| `Press` | ❌ | 缺 `s` |
| `IDLE` | ✅ | I/D/L/E 都在 |
| `HOLD` | ✅ | H/O/L/D 都在 |
| `TAP` | ✅ | T/A/P 都在 |
| `Click` | ✅ | C/l/i/c/k 都在 |

**建议用 `TAP`**（3 字符，直接表达"点一下"），或 `IDLE`（与 `Heat`/`Sleep` 的长度感更一致）。**不要用 `Standby`** —— 缺字符会回落成 `?`，而且 `check_ascii_font.py` 会报"剔除字符会上屏"。

功能设置的标签同理：`"Heat:"`（H/e/a/t/: 都在）可用；`"Auto:"` 缺 `u`，不可用。开关值沿用现成的 `ON`/`OFF`（`fn_toggle` 机制）。

## 7. 状态优先级

HOME 现在是"自检故障码 > 传感器故障 > 关机 > 休眠 > 温度到达 > 加热"。待机文案插在**休眠之后、温度到达之前**即可（待机时温度必然没到，不会冲突）。

自检在 STANDBY 门**之前**执行，所以自检期间显示故障码/自检态的既有逻辑不受影响。

## 8. 已知行为（要写进文档或注释）

1. **自检的测量脉冲仍会施加**：断芯检测需要在 `SELFTEST_HEAT_ON` 阶段给 10% 占空比、约 200ms。温升可忽略，但"手动模式"下烙铁头会极轻微发热——这是安全检测，不建议跳过
2. **STANDBY 不会自动休眠 / 自动关机**：`check_sleep_shutdown` 的入睡判定要求 `state == ACTIVE`，待机态天然不满足。这正好是想要的（待机不该被关机），但要写清
3. **休眠唤醒直接回 ACTIVE**，不回到 STANDBY —— 用户已经点过"开始"，休眠只是省电，不该再要求点一次
4. **`WorkTask_Recover()` 恢复后应回 STANDBY**（手动模式下）：故障恢复是"重新允许加热"，不等于"用户想开始"。注意它现在直接 `Heater_Enable()`，需要加状态判断
5. **前馈学习不受影响**：`learn_ff_hold` 只在 `state == ACTIVE` 学，待机不学
6. **待机时旋钮仍可调目标温度**（HOME 的 UP/DOWN 逻辑不变），只是不加热

## 11. 验证计划

1. 双 target 编译 0 Error / 0 Warning；`prebuild` 全部检查通过
2. 静态：`check_chars`（HOME 新文案的字符）、`check_ascii_font`（确认 `TAP` 全部可编入）
3. 逻辑对拍（可移植成 Python）：状态机迁移表穷举 —— `(state, event, 配置) → 新 state`，验证：
   - 手动模式下，UP/DOWN 不改变 STANDBY
   - 手动模式下，HOME 的 CLICK 第一次启动、第二次进菜单
   - 休眠唤醒不回到 STANDBY
   - 故障恢复后回 STANDBY
4. 真机：
   - 自动模式（默认）：行为与现在完全一致（回归）
   - 手动模式：上电不热、屏幕 `TAP`、点一下开始加热并变 `Heat`、再点进菜单
   - 手动模式下放 5 分钟：不进休眠、不关机（预期）
   - 手动模式下拔插重启：仍是待机（配置持久化）
